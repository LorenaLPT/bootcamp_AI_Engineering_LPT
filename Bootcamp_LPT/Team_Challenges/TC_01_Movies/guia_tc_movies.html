¿De qué va este reto?

Trabajáis con un dataset de películas clásico (MovieLens) y construís un catálogo enriquecido en tres fases: análisis de datos con Pandas, consumo de una API REST (TMDB) y generación de texto con Gemini. Si os sobra tiempo, hay un bonus con salida estructurada en JSON.

Tenéis una semana. Por eso el proyecto está dividido en cuatro notebooks independientes: cada persona trabaja en el suyo desde el primer día y los notebooks se pasan los datos mediante ficheros CSV.

Git Flow del proyecto

Usáis una versión adaptada de Git Flow con tres niveles de rama. La norma de oro: nunca se hace commit directo a main ni a develop; todo entra por pull request.

Estructura de ramas

main ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ versión estable ↑ PR final (merge commit, día 5) develop ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ integración ↑ PR ↑ PR ↑ PR ↑ PR (squash and merge) feature/01-limpieza feature/02-analisis feature/03-tmdb feature/04-gemini

🟢 main

Versión estable y revisada. Solo se actualiza con una PR desde develop al final de la semana.

  • Se mergea con Create a merge commit (no squash)
  • Nunca git push directo

🔵 develop

Rama de integración: aquí se juntan las partes día a día.

  • Se crea una sola vez desde main (día 1)
  • Las features entran con Squash and merge

🌸 feature/nombre

Ramas cortas de un solo propósito.

  • Siempre desde develop actualizado
  • Se borran tras el merge
¿Por qué no squash de develop a main? El squash crea en main un commit nuevo que develop no tiene. La siguiente vez que intentéis llevar develop a main, Git verá historiales distintos y aparecerán conflictos que no existen. Con merge commit las dos ramas comparten historia.

Crear el repositorio en GitHub (persona A)

2

Proteger main y develop

Settings → Rules → Rulesets → New branch ruleset (o Settings → Branches → Add classic branch protection rule). Aplicadlo a main y develop y marcad: ✅ Require a pull request before merging, ✅ 1 approval, ✅ Dismiss stale approvals.

Manejo de conflictos

Un conflicto ocurre cuando dos ramas modifican las mismas líneas. Al hacer git merge origin/develop, Git marcará los ficheros:

<<<<<<< HEAD          ← vuestra versión
...
=======
...                    ← versión de develop
>>>>>>> origin/develop

# Editad dejando lo correcto, borrad las marcas y:
git add fichero_resuelto
git commit --no-edit      # cierra el merge con el mensaje por defecto (no es un "fix")
git push

# ¿Te has liado? Cancela el merge y vuelve a como estabas:
git merge --abort
Conflictos en notebooks (.ipynb): un notebook es un JSON enorme con las salidas dentro, así que sus conflictos son casi imposibles de resolver a mano. Por eso cada notebook tiene un único responsable. Si aun así os pasa, quedaos con una de las dos versiones completas: git restore --ours fichero.ipynb (la de vuestra rama) o git restore --theirs fichero.ipynb (la de develop), después git add fichero.ipynb y rehaced a mano los cambios que falten.

Petición HTTP a la API de TMDB

Notebook 03_tmdb · enriquecer 10 películas con datos de The Movie Database

Endpoint

GET https://api.themoviedb.org/3/movie/{tmdb_id}

El tmdb_id viene de la columna tmdbId de links.csv.

Tareas

  • Cargar las credenciales del .env con load_dotenv() (o getpass si no hay .env)
  • movies10: las 10 primeras películas (por movieId) que tengan tmdbId
  • fetch_movie_details(tmdb_id): una petición con timeout; devuelve overview y homepage (vacíos si son nulos)
  • Si una petición falla (404, timeout…), campos vacíos, aviso por pantalla y seguir con la siguiente
  • Añadir ambas columnas a movies10 y guardar data/processed/movies10.csv

Autenticación

Opción A — Bearer Token (recomendada)

from dotenv import load_dotenv
load_dotenv()
headers = {
    "Authorization": f"Bearer {os.getenv('TMDB_READ_ACCESS_TOKEN')}"
}
resp = requests.get(url, headers=headers, timeout=15)

Opción B — API Key

from dotenv import load_dotenv
load_dotenv()
params = {"api_key": os.getenv("TMDB_API_KEY")}
resp = requests.get(url, params=params, timeout=15)
Probad el endpoint en Postman antes de programar. Es mucho más rápido depurar allí que en el notebook.
No guardéis claves en el notebook ni en ningún fichero que se suba al repositorio. Cuidado también con las salidas: no imprimáis la clave para "comprobar que funciona".
03

Sinopsis en español con Gemini

Notebook 04_gemini · traducir y resumir los overview de TMDB

Mientras movies10.csv no esté en develop, la celda de carga os da datos de prueba. Requiere pip install google-genai python-dotenv.

Tareas

  • Configurar GEMINI_API_KEY en el .env y crear el cliente genai.Client()
  • Definir el modelo en una sola constante: MODEL = "gemini-3.5-flash-lite"
  • summarize_overview_es(overview, title=""): resumen en español de máximo 2 frases
  • Si overview está vacío o es nulo, devolver "" sin llamar a la API; si response.text es None, devolver ""
  • Añadir la columna overview_es, mostrar 3 películas y guardar movies10_es.csv

Esqueleto de la función

import os
import pandas as pd
from dotenv import load_dotenv
from google import genai

load_dotenv()
client = genai.Client()            # lee GEMINI_API_KEY del entorno
MODEL = "gemini-3.5-flash-lite"

def summarize_overview_es(overview, title: str = "") -> str:
    if pd.isna(overview) or not str(overview).strip():
        return ""
    prompt = (
        f"Película: {title}\n"
        f"Sinopsis original: {overview}\n\n"
        "Resume esta sinopsis en español en máximo 2 frases."
    )
    resp = client.models.generate_content(model=MODEL, contents=prompt)
    return (resp.text or "").strip()
Google retira modelos con frecuencia: gemini-2.0-flash ya no funciona. Si recibís 404 / model not found, consultad la lista de modelos actual y cambiad solo la constante MODEL.

Catálogo ampliado con JSON Bonus

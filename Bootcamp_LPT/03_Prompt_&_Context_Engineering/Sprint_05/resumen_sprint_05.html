Lógica y modularización — de script a sistema

Un notebook está bien para explorar; un sistema necesita separación de responsabilidades. En este bloque aprendes a partir un proyecto en módulos con roles claros y a validar los inputs antes de llamar al LLM.

El layout estándar del sprint

mi_proyecto/
├── main.py         # punto de entrada. Orquesta. No lógica.
├── config.py       # modelo, límites, umbrales
├── prompts.py      # build_*_prompt(...). Nada de lógica.
├── logic.py        # las funciones que hacen cosas
├── validators.py   # validar inputs del usuario
├── state.py        # historial en memoria
├── context.py      # seleccionar / filtrar contexto
└── data/           # FAQ, ejemplos
✅ Regla: cada módulo tiene un oficio. Si logic.py construye prompts, es tarea de prompts.py. Mover ese trozo evita que crezca una bola de barro.

Validación de inputs

def validar_consulta(consulta: dict) -> tuple[bool, list[str]]:
    errores = []
    nombre = (consulta.get("nombre") or "").strip()
    email  = (consulta.get("email") or "").strip()
    msg    = (consulta.get("mensaje") or "").strip()

    if len(nombre) < 2:                errores.append("nombre vacío o muy corto")
    if "@" not in email:              errores.append("email sin @")
    if len(msg) < 10:                   errores.append("mensaje muy corto")

    return (len(errores) == 0, errores)

Múltiples respuestas: tabla de handlers vs if/elif

❌ Cadena de if/elif: 
if tipo == "dudas":
    responder_dudas(...)
elif tipo == "incidencia":
    abrir_ticket(...)
elif tipo == "otro":
    ...
✅ Tabla de handlers: 
HANDLERS = {
    "dudas": responder_dudas,
    "incidencia": abrir_ticket,
}
handler = HANDLERS.get(tipo, handler_default)
handler(...)

Estado en memoria

# state.py
historial = []

def append_user(texto):   historial.append({"role": "user", "content": texto})
def append_model(texto):  historial.append({"role": "model", "content": texto})
def ultimos_n(n: int):     return historial[-n:]

Errores típicos

  • Mezclar lógica con construcción de prompts en el mismo archivo: dificulta cambiar el prompt sin tocar la lógica.
  • Hacer print dentro de logic.py: imposible de testear. Devuelve datos y deja que main.py imprima.
  • Historial global sin tope: crece hasta reventar el presupuesto de tokens.
  • No validar el input: el LLM recibe None, "" o garbage.

Prompt Engineering — controlar al modelo

Un prompt bien construido tiene tres piezas: rol (quién es el modelo), tarea (qué debe hacer) y datos (sobre qué). En código, se construye con funciones build_*_prompt parametrizadas, no con strings mágicos pegados en medio del código.

Rol vs pregunta suelta

❌ Pregunta suelta: "¿Qué es Python?"
✅ Con rol: "Eres un profesor de Python para principiantes. Explica qué es Python en 3 frases, sin jerga."

build_prompt parametrizado

ROLES = {
    "profe": "Eres un profesor de Python para principiantes.",
    "revisor": "Eres un revisor técnico que señala 3 mejoras.",
}

def build_prompt(rol: str, tarea: str) -> str:
    return f"{ROLES[rol]}\n\nTarea: {tarea}"

Prompts dinámicos con plantillas

PLANTILLA_RESUMEN = """Resume el siguiente texto en {max_lineas} líneas.

TEXTO:
{texto}
"""

def build_resumen_prompt(texto: str, max_lineas: int = 3) -> str:
    return PLANTILLA_RESUMEN.format(texto=texto, max_lineas=max_lineas)
✅ Separar plantilla y función: la plantilla es un string fijo; la función la rellena. Así puedes cambiar el estilo sin tocar el código que llama.

Inputs del usuario — nunca directamente en el prompt

# Mal: inyectar el mensaje crudo
prompt = f"Clasifica esto: {mensaje_usuario}"

# Bien: separar en bloques delimitados
def build_clasificacion_prompt(mensaje: str) -> str:
    return f"""Eres un clasificador de consultas.

CATEGORÍAS PERMITIDAS: dudas, incidencia, administracion, otro.

CONSULTA:
\"\"\"{mensaje}\"\"\"

Devuelve JSON: {{"categoria": str, "resumen": str}}"""

Los delimitadores (""", ---, <texto>...</texto>) marcan dónde empieza y termina el input del usuario, reduciendo el riesgo de prompt injection.

Salidas estructuradas (JSON)

respuesta = cliente.models.generate_content(
    model=MODEL,
    contents=build_clasificacion_prompt(mensaje),
    config={"response_mime_type": "application/json"},
)

def parsear_clasificacion(texto: str) -> dict | None:
    try:
        datos = json.loads(texto)
    except json.JSONDecodeError:
        return None
    if "categoria" not in datos: return None
    if datos["categoria"] not in {"dudas", "incidencia", "administracion", "otro"}:
        return None
    return datos

Errores típicos

  • Prompts con "haz algo útil": sin rol, sin tarea concreta, sin formato de salida.
  • Pegar el input del usuario sin delimitadores: susceptible a inyecciones.
  • No parsear defensivamente el JSON: una respuesta mal formada tumba el programa.
  • Prompts hardcodeados en 10 archivos: cuando quieras ajustarlo, no sabes dónde está.

Context Engineering — qué información enviar ★

Un LLM no "recuerda" nada entre llamadas: su memoria es lo que le mandas en el prompt. La calidad depende de qué contexto seleccionas, cuánto ruido quitas y cómo gestionas el presupuesto (tokens, latencia, coste).

Contexto y relevancia

Un buen contexto es mínimo pero suficiente. Pasarle al modelo todo el catálogo cuando el usuario pregunta por un solo producto es ruido: sube latencia, sube coste y empeora la respuesta.

def seleccionar_faq(mensaje: str, faq: list[dict], top_k: int = 3) -> list[dict]:
    palabras = set(mensaje.lower().split())
    scored = []
    for item in faq:
        texto = (item["pregunta"] + " " + item["respuesta"]).lower()
        score = sum(1 for p in palabras if p in texto)
        scored.append((score, item))
    scored.sort(key=lambda t: -t[0])
    return [item for score, item in scored[:top_k] if score > 0]

Resumen y compresión

Cuando el historial supera el presupuesto, se comprime: pides al modelo que resuma el historial antiguo en 2-3 líneas y lo guardas como una sola entrada. La ventana corta sigue intacta.

def resumir_historial(historial_antiguo: list) -> str:
    texto = "\n".join(f"{m['role']}: {m['content']}" for m in historial_antiguo)
    r = cliente.models.generate_content(
        model=MODEL,
        contents=f"Resume en 3 líneas la siguiente conversación:\n\n{texto}",
    )
    return r.text
Idea clave El contexto es un recurso: elígelo, mídelo, cómpralo. Elegir lo relevante (filtrar FAQ, trocear historial), medir cuántos tokens cuesta (count_tokens, usage_metadata) y comprar presupuesto cuando conviene (resumen, memoria larga).

Errores típicos

  • Pasarle "todo lo que tienes" al modelo "por si acaso": ruido, coste y peor calidad.
  • Historial infinito: el modelo pierde el foco; el coste explota.
  • No medir tokens: te sorprende la factura de fin de mes.
  • Resumir cada turno: pierdes información útil. Resume cuando pases un umbral.
  • Mezclar historial del usuario con instrucciones de sistema en el mismo bloque.

Live Review — asistente de consultas del bootcamp

Práctica integradora de los tres bloques. Un asistente que recibe consultas, valida, clasifica con Gemini y responde con FAQ, historial y métricas. Es el formato que verás en todos los sprints a partir de aquí: un proyecto con módulos y TODOs que rellenas.

Flujo del asistente

Consulta (nombre, email, mensaje)
   │
   ▼
validators.py  →  errores? → responder error
   │
   ▼
prompts.py  build_clasificacion_prompt(mensaje)
   │
   ▼
Gemini → JSON  →  parsear_clasificacion
   │
   ▼
context.py  seleccionar_faq (top-k)
   │
   ▼
build_chat_prompt(perfil + FAQ + historial + mensaje)
   │
   ▼
Gemini → respuesta  →  state.append_user/model

Las dos fases

Fase 1 — Clasificación

  • validators.py → validar_consulta()
  • prompts.py → build_clasificacion_prompt()
  • logic.py → parsear_clasificacion() + clasificar_consulta()
  • python main.py → demo 1 muestra [OK] / [ERROR]

Fase 2 — Chat con contexto

  • context.py → seleccionar_faq()
  • prompts.py → build_perfil_block, build_faq_block, build_historial_block, build_chat_prompt
  • state.py → append_user, append_model, ultimos_n
  • logic.py → responder_chat()
  • Demo 2: respuesta con FAQ, memoria del nombre y métricas de tokens

Reglas del proyecto

  • No modificas main.py, config.py, gemini_auth.py, gemini_client.py, data/*.json.
  • No usas print en logic.py ni en validators.py: devuelves resultados.
  • Usas los helpers ya hechos: respuesta_ok(mensaje, data) y respuesta_error(mensaje, errores).
  • Siempre pruebas con python main.py.
